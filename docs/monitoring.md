# Monitoring and observability

The API exports `platformops_http_requests_total` and `platformops_http_request_duration_seconds` at `/metrics`; paths use FastAPI route templates and `/metrics` is excluded from its own counters. The app logs JSON to stdout/stderr. Docker uses `docker logs`; Kubernetes uses `kubectl logs -n platformops -l app.kubernetes.io/name=platformops --since=10m`.

For local collection, Compose can run the app with Prometheus and Grafana: set `GRAFANA_ADMIN_PASSWORD` to a temporary local-only value, then use both Compose files. Prometheus scrapes the API every 15 seconds; Grafana is loopback-bound and provisions a dashboard for target availability, request rate, p95 latency and 5xx rate. Metrics are ephemeral and no persistent volume is configured. No actual scrape is claimed until the stack has run and the Prometheus target is observed healthy. For Kind, `kubectl apply -f kubernetes/monitoring/prometheus.yaml` runs a small Prometheus instance that scrapes the app and includes availability/5xx alert rules; access it with a port-forward to its Service. It does not collect Kubernetes node/pod resource metrics or send alerts to an Alertmanager.

The Kubernetes chart's HPA reads CPU resource metrics and is disabled by default. It requires metrics-server and valid CPU requests. The project does not install it automatically. HPA scale events and pod requests/limits should be checked with `kubectl top`, `kubectl get hpa`, and `kubectl describe hpa`. Kind metrics-server may require a specific kubelet TLS configuration; validate before enabling HPA. App metrics can be scraped from the Service by Prometheus; the NetworkPolicy allows the monitoring namespace.

Grafana and Kubernetes/container dashboards are not bundled as misleading empty dashboards. Add them after a real Prometheus stack and kube-state-metrics/cAdvisor availability are verified. Alerts should cover availability, restart loops, sustained CPU/memory pressure and request errors. This local baseline currently has no alert rules.
